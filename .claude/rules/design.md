# Rule: ox CLI design and theming

ox has a unified visual design language. Components are reusable, semantic, and theme-aware. Palette, themes, and light/dark behavior are owned upstream by `sageox-design`. Every reusable component is registered in the catalog (`ox dev catalog`) and documented in `docs/design/`.

**Why a single rule file:** before this existed, every command grew its own ad-hoc rendering. Boxes had three border styles. Colors were hex literals scattered across `cmd/ox/`. Drift was constant. The catalog + this rule fixes that for good.

---

## Rules

### 1. `sageox-design` owns palette, themes, and light/dark behavior

Any change to colors, semantic tokens, light-mode vs dark-mode behavior, or theme structure happens in `/Users/ryan/conductor/workspaces/sageox-design/bogota-v2/tokens/*.yaml` ([github.com/sageox/sageox-design](https://github.com/sageox/sageox-design/)), not in `ox`.

**Why:** ox is one of several platforms (CLI, web, react-native, gitlab) consuming the same token set. Drift here breaks brand consistency across surfaces and pulls the CLI out of sync with the studio at `sageox-design.netlify.app`.

**How to apply:** to change a color or add a semantic token, open a PR in `sageox-design` first, then `cd ../sageox-design && npm run sync` to regenerate `internal/theme/generated.go`.

### 2. Never hand-edit `internal/theme/generated.go`

It's overwritten by `npm run sync`. Edits silently disappear on the next sync.

### 3. Use semantic styles, not raw colors

Never construct `lipgloss.Color(…)` directly, and never hand-write ANSI escapes, outside Bubble Tea code.

In order of preference: reach for an existing semantic style (`StyleSuccess`, `StyleError`, `StyleAccent`, … in `internal/cli/styles.go` and `internal/ui/styles.go`); failing that, build one from a generated token via `theme.Adapt(theme.ColorX)`. A literal passed through `theme.Color("#…")` is permitted for a genuine one-off, but a color used more than once is a missing token — add it in `sageox-design` and re-sync, don't copy the hex. Net-new palette values still land in `internal/theme/generated.go` by sync, never by hand.

This is a correctness rule, not a tidiness one. lipgloss v2's `Style.Render()` always emits 24-bit color, and ox prints past any `colorprofile.Writer`, so a raw `lipgloss.Color` reaches a 256-color terminal as `38;2;R;G;B` — which it misparses into a **background** color, painting whole columns unreadable. `theme.Color` / `theme.Adapt` degrade first. See [docs/design/theming.md § Color depth](../../docs/design/theming.md#color-depth).

Bubble Tea code is exempt: it downsamples its own frames.

**Enforced by:** `TestNoRawLipglossColorOutsideTUI` in `internal/theme/` — fails on any non-TUI file constructing `lipgloss.Color`.

### 4. Search the catalog before inventing a widget

Run `ox dev catalog` (hidden command). Check `docs/design/components/`. Duplicate widgets get rejected at review.

**Why:** ox already has boxes, timelines, sparklines, spinners, selects, prompts, confirms, columns, log-formatting, and markdown. Most "new widget" instincts dissolve once you see the catalog.

### 5. New components are not done until they're in the catalog

A new component needs:
- A registered `Entry` in `internal/uicatalog/entries/<name>.go`
- A spec at `docs/design/components/<name>.md` matching the template
- An `.cast` recording (auto-generated by `make catalog-export`)

A drift-check test fails CI if any of those are missing.

### 6. Respect terminal context

Always branch on `cli.IsInteractive()` / `cli.IsHeadless()`. Bubbletea forms, spinners, and any interactive widget MUST have a non-TTY fallback. See `internal/cli/select.go` for the canonical pattern (numbered prompt fallback).

### 7. `NO_COLOR` is sacred

Every component must render readably under `NO_COLOR=1`. Test it with `NO_COLOR=1 ox dev catalog`. lipgloss v2 does **not** handle this for you — it works only because colors go through `theme.Color` / `theme.Adapt` (rule 3), which resolves `NO_COLOR` to a no-color profile.

Readable under one terminal is not readable under all of them. Check the depth ladder too — `OX_COLOR_PROFILE=ansi256 ox dev catalog` renders what a macOS Terminal.app user sees.

### 8. Single-line, key=value log output stays

Never add multi-line "pretty" log helpers. They break grep, log aggregation, and parsing. Use `internal/cli/logfmt.go` for any structured-log rendering.

### 9. Tokens > styles > raw colors

New semantic concept (e.g., "timeline-now", "public-visibility")? Propose a token in `sageox-design/tokens/`, sync down, then add the matching style. Don't shortcut by inlining a hex value.

### 10. `ox dev catalog` is hidden — do not surface it in `--help`

Keep `Hidden: true` on both `cmd/ox/dev.go` and `cmd/ox/dev_catalog.go`. The catalog is a maintainer tool. End users and AI coworkers learn about it from `DESIGN.md` and `.claude/rules/design.md`; everyone else reaches it via the portal at [sageox-design.netlify.app/2026-05-17-ox-cli-component-catalog/](https://sageox-design.netlify.app/2026-05-17-ox-cli-component-catalog/).

### 11. Tufte minimum

Data-ink ratio matters. Don't add chrome that doesn't carry information. Borders, dividers, and decorative characters must justify their cost in vertical space.

### 12. All components must render in 80 columns

Test with `COLUMNS=80 ox dev catalog`. Lines wider than 80 visible columns get rejected.

### 13. Only `.cast` when there is actual motion

A catalog entry's `Renderer: RendererAsciinema` says "this component IS the motion." A static-frame demo recorded as `.cast` just adds player chrome around a still — it implies motion that isn't there, and reads as worse than a freeze SVG.

**Why:** the asciinema player widget is a *promise* that something will animate when you press play. Breaking that promise (silent screen, no movement) is a UX bug. The catalog must not falsely signal interactivity.

**How to apply:**
- Default new entries to freeze (omit `Renderer`).
- Set `Renderer: RendererAsciinema` only if the demo command produces **observable temporal change** (frames over time, not a single rendered string).
- If you want to *describe* an animated behavior without actually animating, use freeze + the component's spec doc to explain where the motion lives at runtime (see `docs/design/components/spinner.md` for the canonical example).

### 14. No binary catalog assets — ever

Forbidden in `docs/design/`, `dist/design-catalog/`, and the published `proposals/...-ox-cli-component-catalog/` directory:

- `*.png`, `*.gif`, `*.jpg`, `*.jpeg`, `*.mp4`, `*.webm`

Use `.cast` (asciinema recording), `.svg` (snapshot), `.json` (manifest), `.md`, `.html`. Enforced by `make check-no-binary-bloat` and `.gitignore`.

**Why:** text artifacts diff cleanly, theme-switch live (asciinema-player applies theme client-side), and keep repo growth under MB-scale across years of catalog updates. The existing root `demo/demo.gif` predates this rule and is grandfathered.

### 14. Catalog HTML stays self-contained

The exported portal page vendors `asciinema-player.min.js` and `asciinema-player.css` locally — no CDN. Matches the existing proposal pattern (see `proposals/2026-04-25-cast-v1/`) so old proposals keep working forever without network dependencies.
