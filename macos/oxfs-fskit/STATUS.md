# oxfs-fskit — build status & handoff

Standalone **pure-Swift** reimplementation of the oxFS context filesystem on
macOS FSKit, targeting **100% parity** with the Rust `crates/oxfs` reference
(zero Rust in the shipped product). Plan:
`~/.claude/plans/fileprovider-macos-12-1-compiled-lighthouse.md`. Epic: `ox-cpdq`.

## How to run

```
cd macos/oxfs-fskit
make build      # swift build (no Xcode needed)
make test       # swift-testing suite (scripts/test.sh handles CLT vs Xcode)
make run        # oxfs-hello smoke binary
```

First signed-mount workflow (after Xcode setup + signing):

```sh
# Persist a selection outside the source tree, then quit the REPL.
STATE="${TMPDIR:-/tmp}/oxfs-fskit-manual"
swift run oxdirtest --source "$SRC" --state "$STATE"
# In the REPL: select <dir>; quit

make xcode-build                    # install/enable OxfsExtension via Xcode
swift run oxfsmount --source "$SRC" --state "$STATE" --mountpoint "$MOUNTPOINT"
```

`oxfsmount` writes nothing beneath `$SRC`. Its resource/config/state directory is
caller-specified with `--state`, or defaults to an `oxfs-fskit-*` directory in
the app-group container. A security-scoped bookmark grants the extension access
to the source. Live selection changes while mounted are not wired yet.

## FSKit API ground truth (resolved on THIS SDK: macOS 26.5 / Xcode 26)

Settled the research's #1 footgun empirically from
`.../MacOSX.sdk/.../FSKit.framework/Headers/FSVolume.h`:

- FSKit operation protocols are **Objective-C** (`FSVolumeOperations`,
  `FSVolumeReadWriteOperations`, `FSVolumePathConfOperations`, `FSVolumeOpenClose`/
  `Xattr`/`AccessCheck`/`Rename`Operations). The Swift overlay
  (`.swiftinterface`) is thin (124 lines: `UnaryFileSystemExtension`, buffer I/O).
- **Both op shapes are vended** — no hard footgun here. Use whichever:
  - completion-handler: `read(from:at:length:into:replyHandler:)`,
    `lookupItem(named:inDirectory:replyHandler:)`,
    `enumerateDirectory(_:startingAt:verifier:attributes:packer:replyHandler:)`,
    `getAttributes(_:of:replyHandler:)`, `activate(options:replyHandler:)`,
    `deactivate(options:replyHandler:)`.
  - async: the header states an async Swift impl drops the reply handler and
    just returns the value / throws. (Recommend the **async/throws** shape —
    cleaner for calling into `Workspace`.)
- **Read-only**: no single `readOnly` capability flag. Advertise via
  `FSVolumeSupportedCapabilities` + reject mutators with `EROFS`; mount honors
  `FSMountOptionsReadOnly`. (Matches the ExtendFS pattern.)
- Item identity: `FSItem.Identifier(rawValue: UInt64)` ← our stable inode.
- Virtual (non-block) FS: probe/load an `FSPathURLResource`, not
  `FSBlockDeviceResource`. This resource type is macOS 26+, so the mounted
  product target is macOS 26 even though base FSKit APIs begin at 15.4.

## FSKit architecture and observability

Sharvil Shah's [Exploring FSKit](https://objectivebythesea.org/v8/talks/OBTS_v8_sShah.pdf)
provides a useful model for understanding the macOS adapter.

### Object model

FSKit separates three responsibilities:

| FSKit concept | oxFS implementation | Responsibility |
|---|---|---|
| `FSResource` | `FSPathURLResource` containing `.oxfs-mount.json` | Security-scoped backing resource and mount configuration |
| `FSUnaryFileSystem` / container | `OxfsFileSystem` | Probe, load, and unload the resource |
| `FSVolume` | `OxfsVolume` | Present namespace items and implement filesystem operations |

The resource is not the visible filesystem. It grants access to the backing
location from which `OxfsFileSystem` constructs a `Workspace`; `OxfsVolume`
then presents the workspace's immutable namespace snapshot.

```text
FSPathURLResource
  └── .oxfs-mount.json
        └── OxfsFileSystem.loadResource
              └── Workspace + verified cache
                    └── OxfsVolume
                          └── FSItem namespace and open handles
```

`FSPathURLResource` is the appropriate resource type because oxFS is a virtual,
path-backed filesystem rather than a block-device filesystem. The extension
personality must therefore advertise path URL support and reject block,
generic URL, and server resources.

### Activation and mounting

FSKit modules run as app extensions and require explicit installation and
enablement. `fskitd` brokers requests between the VFS boundary and the
extension; the host application is packaging and enablement infrastructure,
not part of the filesystem data path.

A successful build does not prove a usable mount. Validate each boundary
separately:

1. The host application and embedded extension are signed and installed.
2. The FSKit module is enabled.
3. The personality recognizes the path resource.
4. `probeResource` accepts the mount configuration.
5. `loadResource` opens the workspace and reports the container ready.
6. The volume activates and returns its root item.
7. Lookup, enumeration, open, and read succeed through a live mount.

### Capability contract

FSKit capabilities are an externally visible contract, not descriptive
metadata. Advertise only operations whose semantics oxFS implements:

- persistent, 64-bit object identifiers;
- case-sensitive names;
- hidden files;
- no block-resource support;
- read-only behavior enforced by both mount options and `EROFS` responses.

Unsupported symlink, hard-link, xattr, journal, or mutation behavior must not
be advertised optimistically.

### Observability and security boundary

FSKit makes filesystem operations observable in userspace. Keep diagnostics at
the semantic operation boundary—probe, load, activate, lookup, enumerate,
open, read, close, and unload—with operation name, stable object identity,
result, and latency.

Do not log file contents, credentials, source URLs containing credentials, or
security-scoped tokens.

Endpoint Security can independently observe mount and file-open events. It may
be useful for integration testing and operational validation, but it is not a
dependency of oxFS correctness.

## Namespace items vs open files

Traditional Unix filesystems separate a name from an opened file:

- A directory entry maps a name to an inode. `lookup` resolves that namespace
  relationship; it does not keep file content alive.
- `open` creates a file description bound to the exact inode/object at that
  moment. Removing the directory entry behaves like `unlink`: future lookups
  fail, but existing open descriptions continue reading the original object.
- The inode may remain allocated while an open description references it, even
  though it no longer has a live name.

FSKit exposes the same lifetimes through different API objects:

- `FSItem` is the namespace identity returned by lookup/enumeration. It does
  **not** pin cache content. After reconciliation removes its path, a later
  operation that requires a live namespace object returns `ESTALE`/`ENOENT`.
- An FSKit open handle is created by `open(item)`. Open must revalidate the item,
  atomically bind its exact `ContentRef`, retain a verified descriptor, and pin
  that cache object. Reads use that descriptor, not a fresh path lookup.
- Removing the namespace entry does not invalidate an existing open handle.
  Close/reclaim releases the descriptor and the cache pin.

Mental model:

```text
lookup(path) → FSItem/inode identity                 no content pin
                     |
                     | open() revalidates + binds content
                     v
               Open Handle                            pins exact object

namespace removal → future lookup fails; FSItem is stale
                  existing Open Handle keeps reading the verified object

close/reclaim → close descriptor + release pin
```

Pins are process-local open-handle leases, not durable catalog state. Cache
eviction excludes objects whose open count is nonzero. Namespace-generation
protection during reconciliation is a separate, short-lived transaction guard.
